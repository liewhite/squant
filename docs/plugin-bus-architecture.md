# 插件式事件总线架构

> 目标形态：一个进程 = **一条总线 + 若干插件**。
> 交易所、行情源、柜台、策略、观察者一律是插件，装到总线上就开始工作，
> 引擎只负责装配与校验，不持有任何具体实现。

本文只谈设计与特性，不涉及实现语言。

---

## 1. 现状与动机

### 1.1 已经成立的部分

现有框架已经具备这套架构的大半地基，它们**保持不变**：

| 概念 | 作用 | 关键性质 |
|---|---|---|
| 事件族 | 一族事件的路由键类型 + 载荷类型 | 开放扩展点，新增事件族不需要改框架 |
| 事件 | 一个事件族的一份载荷 + 两个时间戳 | 路由键由载荷派生，不单独传 |
| 订阅声明 | "我要收哪个事件族的哪些键" | 是**数据**不是谓词，因此可索引、可自省 |
| 总线 | 按 (事件族, 路由键) 建索引的投递 | 投递是两次哈希，与订阅者总数无关 |
| 组件 | 进程内唯一的有生命周期的单元 | 安装 / 收事件 / 产出事件 / 卸载 四个钩子 |
| 生命周期树 | 谁装的谁负责停、停完子再停父 | 停机顺序是结构事实，不需要全局登记表 |

### 1.2 卡住的地方

问题都出在同一处：**引擎仍然直接持有交易所侧的实现**。

1. **引擎持有三张按交易所索引的表**（公共 REST 客户端、行情流、交易客户端）。
   "接入任意交易所"止步于这三张表装得下的东西。

2. **行情订阅不走总线**，是引擎对行情流对象的直接方法调用。
   于是引擎必须知道每个交易所对应哪个行情流实例。

3. **下单出口是单例**，持有全部交易所的交易客户端，按账户分流。
   下单指令的路由键只到账户，不含交易所——两个交易所的出口无法共存。

4. **启动对齐由引擎自己做**（拉持仓、拉净值、拉挂单）。
   这要求引擎持有私有客户端，还要求它知道"一个账户需要对齐哪几样东西"——那是交易所侧的知识。

5. **一个交易所的接入被拆成三个接口**（公共 REST / 公共行情流 / 私有账户流），
   装配期用一个三元组捆起来。三元组本身没有行为，只是为了让引擎能把它们分别塞进那三张表。

6. **精度对齐发生在策略侧**。tick 大小、最小下单量、张数换算都是交易所的事实，
   却要求策略侧持有全交易所的合约规格表。

### 1.3 目标

- 接入任意交易所、任意数据源、任意执行通道，**引擎一行不改**。
- 引擎退化为两件事：**装配**（把插件挂上总线）与**校验**（指令有没有人接）。
- 所有跨组件交互都在总线上，没有第二条暗线。

## 2. 全局视图

```
                        ┌─────────────────────────────────────┐
                        │              总  线                  │
                        │  按 (事件族, 路由键) 建索引的投递      │
                        │  + 订阅登记  + 生命周期树             │
                        └─────────────────────────────────────┘
        ▲ 发布            ▲ 发布           ▲ 发布          ▲ 发布
        │ ▼ 订阅          │ ▼ 订阅         │ ▼ 订阅        │ ▼ 订阅
   ┌────┴────┐      ┌─────┴─────┐    ┌────┴────┐    ┌────┴─────┐
   │ 行情插件 │      │  柜台插件  │    │ 策略插件 │    │ 观察者插件│
   └─────────┘      └───────────┘    └─────────┘    └──────────┘
        │                  │
        ▼                  ▼
   交易所公共行情      交易所私有接口
```

插件之间**互不知道对方存在**。它们只知道自己订阅什么、产出什么。

## 3. 核心区分：数据面与指令面

这是整套设计的支点。总线上流动两类事件，它们的**校验规则不同**。

| | 数据面 | 指令面 |
|---|---|---|
| 语义 | 发生了什么 | 请做什么 |
| 例子 | 盘口、成交、持仓、订单回报、净值、时钟 | 订阅行情、启动对齐、下单撤单 |
| 无人订阅时 | **正常**。某个标的这一刻没有成交，不是错误 | **致命**。指令没人接就是静默失效 |
| 无人发布时 | 正常。数据源可能暂时没有数据 | 不适用 |
| 校验 | 不校验 | 装配期校验：每条指令必须有接单者 |

### 3.1 为什么这个区分是必要的

一条没人接的指令，失效方式是**完全没有症状**：

- 没人接行情订阅 → 策略永远收不到盘口 → 它只是"很安静"
- 没人接下单指令 → 订单永远不会发出 → 策略以为自己挂了单，实际上什么都没发生
- 没人接对齐请求 → 启动对齐永远不完成 → 策略基于空仓位决策

这三种失效都不会抛异常、不会打错误日志、不会有任何外在表现。
把它们变成**启动即失败**，是这套架构最主要的正确性收益。

而数据面不能这么校验：要求"每个订阅的事件族都必须有发布者"会产生大量假阳性
（一个只在特定条件下才发事件的插件、一个当天恰好没有成交的标的），
假阳性阻止启动，比它想防的问题更糟。

### 3.2 指令面的完备性要求

指令面必须覆盖**引擎原先直接调用实现所做的每一件事**，否则那些调用只能留在暗线上。
清单：

| 原先的直接调用 | 对应指令 |
|---|---|
| 向行情流对象订阅某几路流 | 行情订阅指令 |
| 拉初始持仓 / 净值 / 挂单 | 账户对齐指令（+ 对齐完成应答） |
| 调交易客户端下单 / 撤单 | 下单指令 |
| 周期拉净值 | 无需指令：柜台自己的常驻职责 |

## 4. 路由模型

路由键的选择决定了"这条事件归谁"由投递层回答，而不是由消费方自己判断。
消费方各自判断的失效方式是静默双执行或静默不执行——新增一个交易所时没有任何一处会编译失败。

### 4.1 数据面的三档路由

| 路由维度 | 用于 | 理由 |
|---|---|---|
| 标的 = (交易所, 交易对) | 公共行情 | 一份数据服务所有账户；实盘与影子策略看同一条盘口，不该订两遍 |
| (账户, 标的) | 私有回报（持仓 / 订单回报 / 成交） | 订单归属的结构保证：实盘与影子即便交易同一标的，也从投递层就收不到对方的回报 |
| (账户, 交易所) | 账户级读数（余额 / 净值 / 希腊值） | 策略读不到自己没订阅的交易所的净值，而杠杆闸门正是拿净值算的 |

无路由维度的事件族（时钟）只能全量订阅。

### 4.2 指令面的路由

| 指令 | 路由键 | 理由 |
|---|---|---|
| 行情订阅 | 交易所 | 每个行情插件只接自己那个所的请求 |
| 账户对齐 | (账户, 交易所) | 柜台是"某账户在某所"的角色 |
| 对齐完成 | (账户, 交易所) | 与请求对称 |
| 下单撤单 | **(账户, 交易所)** | 见下 |

### 4.3 下单指令必须带交易所维度

这是现状的一个实质缺陷。

下单指令现在只按账户路由。一旦把中心化的下单出口拆成"每个交易所一个柜台"，
两个柜台就会订阅同一个键，同一条下单指令被投递给两者——**静默双执行**。

因此路由键改为 (账户, 交易所)。随之而来的约束：

- **一条下单指令里的订单必属同一交易所**。
  跨所的一次决策由框架在策略产出后按交易所**自动拆分**成多条，
  而不是要求策略记得分开调用——忘了拆的后果是路由键取了第一张单的交易所，
  另一个所的订单被发去错误的柜台。
- 撤单指令天然带交易所参数，不需要拆。

## 5. 插件目录

所有插件是同一种形态，只在"订阅什么、产出什么"上不同。

### 5.1 行情插件

| | |
|---|---|
| 一个实例代表 | 一个交易所的公共行情接入 |
| 订阅 | 行情订阅指令（本交易所） |
| 产出 | 盘口、成交印记、标记价、指数价、资金费率……（本交易所的任意标的） |
| 凭证 | 不需要 |

**特性**

- 订阅是**增量、幂等**的：同一条流被请求多次只生效一次。
  策略是动态添加的，后来者声明的流集合与先前的必然重叠。
- 一个交易所可以装**多个**行情插件（例如一个接盘口、一个接期权希腊值），
  它们订阅同一个指令键，各自处理自己认得的流类型。
- 数据源不必是交易所：历史回放、第三方数据商、另一个进程的桥接，
  只要它接行情订阅指令并产出行情事件，对总线而言没有区别。

### 5.2 柜台插件

| | |
|---|---|
| 一个实例代表 | **一个账户在一个交易所上的执行与汇报** |
| 订阅 | 下单指令、账户对齐指令（本账户本所） |
| 产出 | 订单回报、成交、持仓、余额、净值、对齐完成应答 |
| 凭证 | 需要（虚拟柜台除外） |

**职责范围**——柜台是"交易所侧知识"的唯一归属地：

1. **执行**：把币本位的下单意图换算成交易所格式（张数、tick 取整），下发。
2. **精度裁决**：对齐后交易所收不下的单（低于最小下单量、被取整成零），
   以**拒单回报**回流，走与"交易所明确拒绝"完全相同的路径。
   ——不需要第二套机制，策略侧的挂单登记因此得到统一的清理。
3. **汇报**：私有推送流解析成回报事件，并**维护仓位**（见 5.6）。
4. **对齐**：收到对齐指令时拉取当前持仓 / 挂单 / 净值并发布，完成后发应答。
   交易所没返回的标的要显式推零仓，否则策略永远等不到那个标的的初始值。
5. **净值刷新**：净值随行情持续变动却没有推送，只能周期拉取。
   这是柜台自己的常驻职责，不需要外部指令。

**替身形态的行情面**

一个虚拟柜台若要**替换掉整个交易所**（策略对真假无感知），它还得管行情：
撮合用**实时**行情、策略看**延迟**行情，同一条行情要有两个到达时刻，就不能只有一条路径。
做法是把上游行情源装在柜台自己的**私有总线**上：

```
上游行情源 ──> 私有总线 ──> 柜台 ──┬──> 撮合（实时）
                                  └──> 延迟 ──> 主总线 ──> 策略
```

行情订阅指令反向穿过来：主总线 → 柜台 → 私有总线 → 上游。

私有总线上的中继必须**收下上游的一切**，而不是按内置行情事件族枚举着收——
用户自定义的行情源同样是一等公民，枚举着收会让它在这里静默消失（契约校验通过、
订阅指令也转下去了，数据却没人接着往外送）。反过来，中继必须**跳过指令面事件**：
指令是从主总线流进来的，原样转回去会让它在两条总线之间无限弹跳。

**特性**

- **虚拟柜台与真实柜台在总线上完全同形**。
  一个模拟撮合器只要订阅同样的指令、产出同样的回报，策略就无法分辨。
  这是"同一份策略逻辑同时跑实盘与影子盘"的结构基础。
- 一个交易所可以同时挂**多个**柜台，只要账户不同：
  一个真实账户 + 若干影子账户并行，互不知情。
- **没有凭证就不装柜台**。"这个所能不能下单"因此是装配期的事实
  （装没装柜台），不是运行时才发现的错误。

### 5.3 策略插件

| | |
|---|---|
| 一个实例代表 | 一份策略逻辑绑定到一个账户 |
| 订阅 | 声明的行情 + 框架补齐的私有回报 / 账户读数 / 时钟 |
| 产出 | 下单指令、自定义事件（指标、信号） |

**特性**

- 策略**不知道自己跑在哪个账户上**。账户是装配期绑定的构造能力，不是可读数据。
  同一份逻辑因此能同时跑实盘与影子盘，而策略里写不出任何依赖"我是哪个账户"的分支。
- 订阅声明与事件处理**合一**：声明从处理器派生，
  "订阅了不处理"和"处理了没订阅"在结构上不可能发生。
- 框架补齐三类订阅（私有回报、账户读数、时钟），不留给策略选择——
  漏订一条成交回报会让本地仓位与交易所长期发散，而这没有任何外在症状。
- 策略产出的下单意图在框架侧统一施加两件事：分配委托编号、以币本位登记挂单。
  精度对齐**不在这里**（见 5.2）。
- 框架补齐的私有回报是**持仓与订单回报**两样，**不含成交明细**：
  仓位归柜台算之后（见 5.6），策略侧没有任何东西非成交不可。
  想看成交明细（滑点统计、成交记录）的策略自己声明——那本来就是它该说的话。

### 5.6 仓位归柜台

**仓位是柜台的账本，不是策略自己累加出来的。**

初值来自启动对齐（交易所真实持仓），之后每笔成交进账本。策略只读仓位快照。

原先这份账在策略侧：每个策略实例用成交自己累加一份，而交易所持续推来的权威读数
被全部丢弃（只认第一条）。于是同一个事实有三份实现——策略累加的、交易所报的、
虚拟柜台账本里的——只用其中一份，且本地账一旦漂移就永远发现不了。

#### 契约只有一条：仓位快照先于订单状态发出

**这条不是为了「读到最新的数」，是为了消灭一个会导致重复下单的中间状态。**

订单终态到达时，策略本地的挂单登记会被移除。如果此刻仓位还没更新：

```
OrderUpdate(Filled) → 挂单消失
                      仓位还是旧的
策略看到：没有挂单 + 仓位不够 → 再下一单
```

策略要回答的是「我还需要下多少」= 目标 − 当前仓位 − 在途挂单。**这三个量必须来自
同一时刻的快照**，否则不同步的方向恰好是危险侧。

反过来的中间状态（仓位先增、挂单还在）是保守的——策略最多少下一单。所以顺序不是
风格问题，是**危险侧朝哪边**的问题。

这条由构造保证：仓位与订单状态出自**同一条订单回报**，柜台记完账先发仓位再发状态，
不依赖任何交易所的推送次序。

#### 记账的唯一依据是订单回报的累计成交量

一条订单回报里，「这单成交到 0.5 了」与「这单终态了」是**同一个事实的两面**，天然同步。
柜台据它记账，上面那条顺序才构造得出来。

**成交明细不参与记账**。让它也参与，就得为「只给单笔量的交易所」本地累加出一个
「我们造的累计量」——而那不是交易所的真相。一连串补丁由此而来：

| 补丁 | 因为造了假真相 |
|---|---|
| 本地累加 | 单笔量凑不出累计量 |
| 按成交 id 去重 | 本地累加需要幂等 |
| 浮点容差 | 本地累加会漂 |
| 累计量倒退告警 | 两个来源会不一致 |
| 累加器超龄清理 | 多了一份要管的状态 |

源头单一之后，这些全都不存在。成交明细只变成总线上的成交事件，服务于绩效统计、
成交记录、滑点分析——它们不读仓位。

#### 柜台需要记住每张单已记账的累计量

从累计量推导增量，必须记住上一次的累计量。这不是仓位的副本，是**差分的前值**，
生命周期从首次成交到订单终态。

两处容易错：

- **对齐时必须用既有挂单的已成交量填回它**。否则对齐后第一条回报会把对齐之前就已成交的
  部分再记一遍——拉到的仓位里本已含着那 0.3，而记账进度是空的，于是累计 0.5 被当成增量 0.5。
- **订单终态后不能立刻清**。状态与成交常走两条频道，晚到的那条会被当成新成交。
  终态只立墓碑，过一分钟再清；**非终态的永远不清**——清掉一张还活着的订单的进度，
  下一条累计量就会从零重记。

#### 汇报面只解析，不发布

私有推送流不再直接发事件到总线，只把解析结果交给柜台。这让三件本该由柜台负责的事
不再漏出去：**顺序**（各交易所推送次序不同）、**记账**（得先记账才谈得上发仓位）、
**账户归属**（谁的回报是装配期的事实，只有柜台知道）。

各交易所适配层因此只剩它真正独有的部分：怎么把交易所的 JSON 读成统一的形态。

#### 记账依据是累计量，不是本次增量

汇报面报的是**该订单到此刻为止的累计成交量**，柜台只记 `累计 − 已记账` 那部分。
三种麻烦一起消失：

| 麻烦 | 为什么不再是问题 |
|---|---|
| 重复推送 | 增量为零，什么都不发生 |
| 跨频道乱序 | 谁先到谁触发记账，后到的增量为零 |
| 丢一条推送 | 下一条的累计量把账补回来 |

只给单笔量的交易所，由该适配层自己累加（它有订单编号，累加是本地的）。

**订单终态后不能立刻清记账进度**：状态与成交常走两条频道，"已成交"先到、那笔成交的
推送随后才到是常态——清了进度，晚到的那条会被当成新成交记第二遍，仓位凭空翻倍。
终态只立墓碑，过一分钟再清。

#### 对账：只告警，不覆盖

搬到柜台之后，「我累加的」与「交易所报的」第一次落在同一个角色手里，对账才成为可能。

柜台手里有**三条互相独立的渠道**在说同一件事：

| 渠道 | 怎么来的 |
|---|---|
| 订单回报账本 | 累计成交量记出来的 —— **权威**，发到总线的就是它 |
| 成交明细账本 | 逐笔成交累出来的 —— 第二意见 |
| 交易所仓位读数 | 交易所直接推的（不进总线） |

按节拍两两比对。**谁跟谁对不上，决定了这是什么性质的问题**：

| 比对 | 不一致意味着 | 怎么处理 |
|---|---|---|
| 订单回报账 ↔ 成交明细账 | 两者都是我们自己记的，来源却完全不同。对不上说明**我们这边有 bug** —— 少解析了一条推送、字段读错、去重去多了 | 改代码 |
| 订单回报账 ↔ 交易所读数 | 账户被外部改了（强平、手动干预、资金费），或漏收了回报 | 人去交易所看一眼 |

**这个区分才是三方对账的价值。** 两方对账只能说「对不上」，说不清该改代码还是该找人。

**偶尔一次不算数**：成交与仓位走不同频道、订单回报与成交推送也不同步，任一时刻三本账
都可能差着一笔。连续若干次仍然对不上才升级为告警——时序窗口撑不了那么久，撑得住的只有
真问题。中间那几次留 debug，报出来只会把真问题淹掉。

至于「交易所推的是整个账户，里面有别人的标的」——那不是噪声，是**职责边界**：
柜台管的是引擎交给它对齐的那些标的，别的标的的报告在入口就分流掉了，不进记账也不进对账。

**不覆盖**是因为跨频道没有顺序保证：成交与仓位走的是两条频道，交易所先推仓位、
后推那笔成交是可能的——覆盖之后再把那笔成交记进账本，就双重计数了。

那漂移怎么修？**发一条账户对齐指令**：REST 查的是快照，不参与推送的流竞争，
柜台据此重置账本并广播新仓位。

> **检测用推送**（便宜、及时），**修复用 REST**（权威、无竞态）——两件事分开。

触发漂移的是账本看不见的东西：强平、手动干预、资金费结算、任何一笔漏收的成交。

#### 仓位快照不含未实现盈亏

恒为 0。那要估值价，而真实柜台不订阅行情、算不了。两边都留 0 是有意的——
一边有值一边没有，策略读到的东西就随部署形态而变。要盈亏读账户净值，那是柜台确实算得出的。

### 5.4 时钟插件

产出定时节拍，驱动订单超时检测一类的周期任务。

节拍是**数据**不是指令：没有时钟插件时，超时检测不工作，但这由引擎必定装载它来保证，
不需要校验。

### 5.5 观察者插件

订阅任意事件，不产出（或只产出自定义事件）。成交记录、绩效跟踪、指标导出、监督者。

**特性**

- 观察者用全量订阅声明，**不产生标的归属**——它不交易那些标的，
  因此不占用标的独占登记、不做启动对齐、不被补齐私有回报。
- 全市场扫描器要看几百个标的一个都不交易，它需要的只是"让数据真的流过来"，
  即代它发一次行情订阅指令。

## 6. 装配与契约校验

### 6.1 引擎剩下什么

引擎不再持有任何交易所侧实现。它只做四件事：

1. **安装插件**——挂上总线，纳入生命周期树。
2. **添加策略**——标的独占检查 → 契约校验 → 启动对齐 → 订阅行情。
3. **移除组件**——停子树、等收尾、释放标的登记。
4. **停机**。

### 6.2 契约校验规则

**规则：策略将要发出的每一条指令，其 (事件族, 路由键) 上必须已经有接单者。否则拒绝启动。**

校验项从策略的订阅声明直接派生，不需要策略额外声明任何东西：

| 校验项 | 键的来源 |
|---|---|
| 行情订阅指令有人接 | 声明的行情流所属的交易所 |
| 账户对齐指令有人接 | 声明的标的所属的交易所 × 绑定账户 |
| 下单指令有人接 | 同上 |

#### 接单者 ≠ 旁观者

数的是**定向订阅**（"我要这个键的事件"）的订阅者，**不含全量订阅**（"这个事件族我全收"）。
这两者的差别正是接单者与旁观者的差别：

- 一个订阅了全部下单指令的**意图记录器 / 监控插件**是旁观者，它不会执行任何订单。
  把它算作接单者的话，柜台没装也能通过校验，而订单永远发不出去——恰是这道校验要防的失效。
- 接单者**必然**是定向订阅的：它服务的是某个确定的账户与交易所。
  一个全量订阅的柜台连"哪些单归自己"都没想清楚。

#### 独占指令：恰好一个接单者

下单与对齐是**独占指令**——同一个键上只能有一个接单者。

路由键带上交易所维度防住的是"拆出多个柜台"这一种双执行成因，防不住**同一个键上装了两台**
（例如真实柜台与虚拟柜台都装在 (实盘, 某所) 上）。后者只能靠装配期数一数：
装第二台时直接拒绝，检查排在插件启动之前。

运行期它唯一的症状是仓位莫名其妙翻倍。

**行情订阅不是独占指令**：一个交易所挂多个行情插件是正常的（一个接盘口与成交、
一个接期权希腊值），它们各自认领认得的流类型。行情多订一次最多浪费一次往返，
与多下一次单不是一回事。

### 6.3 为什么不要"我提供什么"的声明

一个自然的设计是让每个插件声明它发布哪些事件族，装配期做 需求/供给 交叉检查。**不采用**，理由：

1. **订阅本身就是声明**。插件为了工作本来就必须订阅它要接的指令，
   查订阅登记表即可，不需要第二份事实。
2. **多一份声明就多一处会写错、会漏写的事实**，
   而漏写的表现是**启动被误拒**——比它想防的问题更糟。
3. **供给声明表达不了精度**。行情插件能提供的是"本所任意标的的盘口"，
   那是一个无限集合；写成"我提供盘口"就丢掉了交易所维度，
   于是"策略订了 A 所的盘口，但只装了 B 所的行情插件"照样通不过检查——
   假阴性，白写。
   而指令面的键是有限且精确的（交易所、账户交易所），查订阅登记表天然精确到键。
4. 数据面本来就不该校验（见 3.1）。

**代价**：策略订阅了一个纯粹自定义的事件族（例如另一个策略产出的指标），
而那个产出方没有装载——这种情况检查不出来。
判断：这类失效罕见（自定义事件族只在策略之间使用），
且为它引入一份全局声明的成本高于收益。

### 6.4 标的独占

一个标的在一个账户下最多归一个策略实例。

私有回报按 (账户, 标的) 路由，两个实例占同一个键就会互相收到对方的成交与订单回报——
各自把账户总仓位当成自己的敞口，撤下一个还可能撤掉另一个的活单，全都没有外在症状。

实盘与影子盘跑同一标的是**允许**的：账户不同，键就不同。
这正是该约束要保住的场景——若定成"一个标的一个策略"，同一份逻辑就没法两边同时跑。

检查与登记分两步，使拒绝发生在策略**启动之前**：起来了再拒绝就得再把它停回去。

## 7. 启动顺序：从调用顺序到因果链

### 7.1 要保住的性质

**策略在拿到初始仓位之前，不能看到第一条行情。**

否则它基于"仓位为空"这个错误前提做第一次决策——可能是重复开仓、可能是对着不存在的敞口对冲。

现状靠**调用顺序**保证（引擎同步地拉完持仓再订行情）。
插件化之后引擎不再持有私有客户端，这个顺序必须换一种方式表达。

### 7.2 因果链

添加一批策略时：

```
1. 装配策略插件，订阅总线
       │   （先订阅，此后发布的事件都不会丢）
       ▼
2. 契约校验：这批策略要发的指令都有人接吗
       │   （不通过 → 启动失败，策略尚未运行，无需回滚）
       ▼
3. 发出账户对齐指令（每个 账户×交易所 一条，带请求编号）
       │
       ▼   柜台拉取并发布：持仓 → 净值 → 挂单，然后发对齐完成应答
4. 等待对齐完成应答（按请求编号认领）
       │
       ▼
5. 发出行情订阅指令
       │
       ▼   行情插件向交易所订流，数据从此刻开始流动
```

### 7.3 关于"请求—应答"

发布订阅模型上表达请求—应答通常很别扭，因为**失败无法表达**：发出去没人应，等多久算超时？

这里不别扭，原因是**故障模型消除了第三种结局**：

- 对齐成功 → 发应答
- 对齐失败 → 抛异常，进程终止（账户状态没对上就开始交易，比不启动危险得多）

不存在"既没成功也没失败"的悬空状态。而"没人接"这一种，已经被第 2 步的契约校验挡在前面。

应答带**请求编号**，使等待方只认领自己那一条，不会把上一轮的残留应答当成本轮完成。

### 7.4 影子账户不对齐

影子账户从零开始——没有历史仓位与挂单要恢复。
拿真实交易所的持仓去对齐一个模拟账户是错的：那是别人的仓位。

判定用穷举分支而不是相等比较：将来多一种账户类型时，这里会因为不完整而失败，
逼人来决定它要不要对齐；相等比较则会把它默默归进"不对齐"那一侧。

## 8. 生命周期与依赖

用户提出的原始设想里有一条：**"某个插件退出，总线通知依赖它的插件，默认自行退出。"**
方向对，但需要拆成两种不同的依赖，否则会掉进一个没有正确答案的问题里。

### 8.1 两种依赖，不要混成一张图

| | 数据依赖 | 生命周期依赖 |
|---|---|---|
| 含义 | 谁的事件喂给谁 | 谁托管谁 |
| 形状 | **任意有向图，天然成环** | **树** |
| 例子 | 策略依赖柜台的成交回报，柜台依赖策略的下单指令——已经是环 | 引擎装载柜台；策略装载它的子组件 |
| 用途 | 不能用来定停机顺序 | **就是停机顺序** |

数据依赖成环是这个领域的本质，不是设计缺陷：执行链路本来就是"策略 → 柜台 → 策略"的闭环。
拿它做拓扑排序无解。

### 8.2 停机顺序：依赖方先收尾，被依赖方最后走

**策略的卸载钩子里有真活要干——撤单。**

如果柜台先退出、再通知策略退出，策略的撤单指令发到一条没人接的信道上，
挂单就留在交易所无人跟踪。

正确顺序是：**依赖方先收尾完毕，被依赖方最后走。**

这恰好就是生命周期树已有的语义：

```
停一个组件：
  1. 递归停完它的所有子组件，等到它们的卸载钩子真正跑完
  2. 送出停止信号，唤醒自驱动循环
  3. 从总线摘除订阅（不再有新事件进来）
  4. 关闭邮箱（已缓冲的事件仍被消费完）
  5. 等自己的卸载钩子跑完
```

只要保证**生命周期依赖方向 = 树的父子方向**（先装的后停，后装的先停），
顺序就自动正确，不需要任何新机制。

### 8.3 卸载时的两条保证

1. **卸载钩子发出的最后一批事件必须投递得出去**——那时总线与下游都还活着。
   所以摘除订阅排在卸载钩子之后。
2. **卸载钩子不可被打断**。它要发的是撤单一类的指令，被打断等于漏发。

### 8.4 邮箱与停机

停止信号就是**关闭邮箱**：先摘除订阅，再关闭。已缓冲的事件仍会被投递完，
消费者处理到那时才退出——停机时邮箱里积压的成交回报不会被丢掉。

不能写成"停止信号与事件流二选一"：两路同时就绪时选谁不确定，
挑中停止信号就把邮箱里没处理的事件连同状态更新一起丢了。

### 8.5 明确不做：通用依赖图热插拔

不实现"总线维护插件间依赖图、按图级联通知退出"。理由：

- 数据依赖成环，不能定序（8.1）
- 生命周期依赖是树，已经有正确答案（8.2）
- 引入拓扑排序 + 环处理 + 部分失败，换来的东西树已经给了

**替代方案**：移除一个插件时，若它接的指令信道上已经没有别的接单者，记录告警并列出
**空掉的信道**（不是"受影响的插件"——发指令的一方没有被追踪，也不该为此建一张表）。
这是可观测性，不是自动化——"要不要把依赖它的东西一起停掉"是运维决定，
框架替人决定会在不该停的时候停。

## 9. 故障模型

### 9.1 fail-fast 是默认，且不做局部重启

任何插件的异常级联终止整个进程，由外层重新拉起，靠启动对齐恢复一致。

**不做局部重启**：一个崩掉的策略留下的挂单与仓位归谁管，是个没有好答案的问题；
而"进程重启后重新对齐"有答案。

### 9.2 正常撤下 ≠ 崩溃

这两件事要分开：

| | 正常撤下 | 崩溃 |
|---|---|---|
| 触发 | 显式移除（策略轮换、监督者降级） | 未预期的异常 |
| 卸载钩子 | 跑完（撤单） | 不保证 |
| 后果 | 局部生效，进程继续 | 整进程终止 |

**热插拔只对前者成立。** 把崩溃也做成局部处理，等于把 9.1 的判断推翻。

### 9.3 什么算错误

| 情形 | 处理 |
|---|---|
| 交易所明确拒绝（订单确定未成立） | 正常业务结果，以拒单回报回流策略 |
| 精度对齐后交易所收不下 | 同上——走同一条路径，不需要第二套机制 |
| 网络错误 / 超时 / 5xx（订单是否成立**不确定**） | 致命。本地状态无法保证正确，终止 |
| 限频 / 封禁 | 致命。"订单生命周期自然限速"的假设已被打破，按拒单回流会形成重试风暴 |
| 私有流断线 | 致命。断线期间的推送无法回放，"重连恢复"造成静默的状态发散 |
| 撤一张已成交/不存在的单 | 容忍。终态以推送为准 |

### 9.4 邮箱无界

每个订阅者一条无界邮箱，发布方不因慢消费者阻塞。

**不能换成有界邮箱**：有界 + 尽力投递会在队列满时静默丢事件，
而丢掉一条成交回报的后果是本地仓位与交易所长期不一致，且没有任何外在症状。
真正的背压问题应当在消费者侧暴露（滞后告警），而不是靠丢事件掩盖。

代价：订阅者停掉后若不摘除订阅，它那条邮箱会继续累积事件直到进程退出。
所以摘除订阅不是可选的收尾动作。

## 10. 四种运行形态的一致性

同一份策略逻辑要能在四种形态下跑出可比的结果。

| 形态 | 行情来源 | 执行/回报来源 | 时间 |
|---|---|---|---|
| 实盘 | 真实行情插件 | 真实柜台 | 墙钟 |
| 模拟盘（替身） | 真实行情插件 | **虚拟柜台替换真实柜台** | 墙钟 + 真实定时器 |
| 影子盘（并行） | 真实行情插件（共用） | 虚拟柜台**与真实柜台并存**，账户不同 | 墙钟 + 真实定时器 |
| 回测 | 历史数据源 | 虚拟撮合 | 虚拟时间优先队列 |

### 10.1 共享的部分

- **撮合内核**：同一个纯状态机（下单到达 / 撤单到达 / 行情到达 → 新状态 + 若干延迟回报）
- **策略步**：同一份逻辑核心（过滤订阅范围、更新状态、产出指令）
- **账本**：同一份

差异**只在驱动层**：实盘是并发线程 + 真实定时器，回测是单线程 + 虚拟时间队列。
"延迟 D 后做某事"在前者是排一个定时任务，在后者是入队到 `当前时刻 + D`。

### 10.2 延迟必须建模

影子盘存在的理由是"预测实盘表现"。若它没有下单在途与回报回传的延迟，
就会系统性偏乐观，据此得出的结论无法外推到实盘。

### 10.3 回测不经总线

回测在单线程循环里直接调用策略步，不经总线。为此**判据必须同源**：
"这条事件归不归这个订阅者"在总线（投递索引）与回测（直接过滤）用的是**同一份**订阅声明。
两者若各写各的，恰好等价也只是巧合——改了其中一处，另一处不会失败，
失效方式是某个订阅者静默收不到事件。

### 10.4 指令面不进回测

新增的控制指令（行情订阅、账户对齐）**只在实盘装配路径上**：

- 回测的数据源是文件，不需要订阅
- 回测的账户从零开始，不需要对齐

因此回测路径不受影响，不存在"实盘与回测分叉"的新风险。

这也是**控制指令数量要压到最少**的理由：每多一条上总线的控制指令，
回测就多欠一份实现，或者多一处分叉。

### 10.5 确定性

回测必须"同一输入必得同一结果"：

- 委托编号用确定性自增，不用随机
- 事件时间戳取虚拟时间，不读墙钟
- 同刻事件按入队序出队
- 框架内部任何遍历/分组的产出顺序必须确定（例如跨交易所拆分下单指令时按交易所排序）

## 11. 边界与非目标

### 11.1 总线只在进程内

投递路径无锁、无分配，两次哈希查找。盘口是热路径。

**"插件式"不意味着跨进程装载**。要跨进程，写一个桥接插件把事件转出去 / 接进来，
内核一行不动。序列化成本量级完全不同，不该混进内核的设计约束。

### 11.2 不做存活心跳

同进程内的插件就是线程，线程死了就是异常，异常已经级联终止。心跳探不出更多东西。

真正需要探活的是**外部连接**（连接断开、行情长时间静默）——
那是各插件自己的职责（例如空闲超时看门狗把"无错误可抛的静默停滞"转化成可抛的错误），
不是总线内核的。往内核加心跳只会让内核变胖。

### 11.3 不做通用依赖图热插拔

见 8.5。

### 11.4 不做局部重启

见 9.1。

## 12. 迁移路径

分阶段，每阶段独立可验证。

| 阶段 | 内容 | 验证 |
|---|---|---|
| 1 | 指令面：定义控制指令事件族；总线提供"这个键有没有订阅者"的查询 | 单元测试 |
| 2 | 下单指令路由键加交易所维度；跨所决策自动拆分 | 现有账户隔离 / 执行流测试 |
| 3 | 精度对齐从策略侧移到柜台侧；收不下的单以拒单回流 | 现有精度 / 挂单登记测试 |
| 4 | 定义行情插件与柜台插件两种形态；各交易所接入改写为这两种插件 | 现有交易所适配测试 |
| 5 | 引擎瘦身：删掉三张表、三元组、中心化下单出口、中心化净值刷新 | 现有引擎集成测试 |
| 6 | 虚拟柜台 / 影子柜台 / 回测适配 | 现有模拟盘与回测测试 |
| 7 | 各启动器适配 | 手工冒烟 |

### 12.1 会被删除的概念

| 删除 | 原因 |
|---|---|
| 交易所接入三元组 | 三个接口捆在一起只是为了塞进引擎那三张表；表没了，捆绑也没了 |
| 公共行情流接口 / 私有账户流接口 | 它们本质就是插件——"启动时给我总线"就是安装钩子 |
| 中心化下单出口 | 拆进各柜台 |
| 中心化净值刷新 | 并进各柜台（净值是柜台的职责） |
| 引擎持有的合约规格表 | 精度是交易所的事实，归柜台 |

### 12.2 新增的概念

**只有一个**：指令面（一组控制指令事件族 + 一条校验规则）。

没有新增"插件"这个类型——插件就是现有的组件形态。
同一件事两个名字，正是要避免的。
