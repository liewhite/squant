# 实时看板

一个只读的 Web 看板：各标的的行情、仓位、挂单，以及各账户的净值与余额。

```
总线 ──> DashboardActor.onEvent (actor 线程, 唯一写者)
              │
              └──> AtomicReference[BoardSnapshot]  ←── HTTP 线程只读
                                                          │
                                        BoardView ────────┴──> JSON / 页面
```

## 装上它

看板是一个普通的 `Actor`，和柜台、行情源同一种形态，所以装配方式也一样：

```scala
Engine.run(plugins = Vector(gateway, marketFeed)) { engine =>
  engine.install(DashboardActor(port = 8123))   // 一行
  engine.addStrategy(strategy, AccountId.Live)
  engine.awaitShutdown()
}
```

生命周期归引擎：停机时 HTTP 服务随组件一起关掉，端口被释放（`ctx.manage` 登记，
不靠 JVM 退出兜底）。

只看页面长什么样（合成数据，不接交易所）：

```
sbt "demo/runMain demo.DashboardDemoLauncher 8123"
```

已经接上的启动器：`StockSpreadLauncher`（三所股票永续价差监控，端口由第 4 个参数给，
默认 8123，给 `0` 表示不起）。

| 路径 | 内容 |
|---|---|
| `/` | 页面，1 秒轮询一次 |
| `/api/board` | JSON |
| `/docs` | Swagger UI |

## 三条设计判断

### 1. 它是观察者，不去读 StateManager

框架里已经有一份权威状态（`hft.state.StateManager`），但看板**不读它**，而是自己订阅总线、
折叠出一份不可变快照。两个理由：

- 那份状态是可变的、只归策略执行器的 actor 线程所有，从 HTTP 线程读它是数据竞争；
- 它按**策略实例**建，一个进程里有几个策略就有几份，每份只看得见自己订阅的标的 ——
  而看板要看的恰恰是全进程在做什么。

代价是这里有第二份"从事件重建状态"的代码。为了让它可控，凡是**判断**都复用框架那一份的
**实现**，不在看板里重写：

- 挂单在不在场只认 `OrderStatus.isTerminal`；
- 钱包的三条规则（全量整表替换 / 逐币种只覆盖一个键 / 全量之前缺失不等于 0）归
  `hft.domain.WalletState`，`StateManager` 与看板用的是同一个类型。
  它们从前各写一遍、各自在注释里指向同一份文档 —— 而**文档是依据，不是实现**，
  它保证不了两份实现同步。

订阅什么与怎么折叠也是同一张表（`BoardSnapshot.folds`）：加一个 topic 就必须同时给出它的
折叠规则，否则编译不过。两份列表错开的失效形态是"事件在计数、心跳在跳、页面上那一列永远是空的"。

收益是看板与交易路径完全隔离：它算错了，不会有一分钱因此下错单。

### 2. 每个数字都带着它的年龄

一个 4 分钟前的盘口和一个刚到的盘口，在页面上必须长得不一样。这不是锦上添花 ——
把陈旧读数显示成正常读数，就是这个仓库反复在修的那类问题的展示层版本：
**"不知道"被显示成一个看着正常的值**。

所以：

- `Stamped[A]` 把"值"和"它什么时候到的"绑在一起，年龄在**读取时刻**才算出来
  （否则页面上的"3s 前"会永远停在 3s）；
- 时刻取本地接收时刻（`Event.localTs`）而不是交易所时间戳 —— 年龄要拿本地墙钟去减，
  两边必须同一个钟，否则减出来的是"陈旧度 + 时钟偏斜"；
- 页面按阈值变色，但**只对流式读数**（见下表）；
- 没有读数显示 `—` 而不是 `0`。**0 是一个合法的价格与仓位取值**，用它表示"这条读数还没到过"，
  页面就再也分不出"空仓"与"仓位读数没来"；
- JSON 里同理：`transientNone` 与 `transientEmpty` 都关掉，缺读数是 `null`、空列表是 `[]`，
  而不是整个字段消失（顺带一提，字段消失会让页面的 `rows.length` 直接抛 TypeError）；
- `eventsApplied == 0` 单独显示为"总线上一条事件都没来过" —— 那是**看板没接上**
  （订阅漏了、引擎没起、行情源没连上），不是"无事发生"；
- 顶上有心跳（距最后一条事件多久）。整个数据流断了，这里先红。

**年龄对两类读数的含义不同，不能共用一套阈值：**

| 类别 | 例子 | 年龄的含义 | 页面 |
|---|---|---|---|
| 流式 | 盘口、标记价、最近成交价 | **陈旧度** —— 交易所在持续推，停了就是断流 | > 5s 黄，> 30s 红 |
| 变更驱动 | 仓位、挂单、最近成交、净值、余额 | **距上次变化多久** —— 不动是常态 | 只显示，不上色 |

仓位由柜台在成交入账与启动对齐时才推，净值按 `accountRefreshMs`（默认 10s）周期发。两类共用
5s/30s 的话，真实柜台下**每个不动的仓位 30s 后必然标红**、净值每个刷新周期的后 5 秒变黄 ——
满屏假红会很快被当成噪声忽略，于是真断流的时候反而看不出来。"数据流还活不活着"由顶部心跳
（`lastEventAgeMs`）与流式读数回答。

> 这条在浏览器里验证时没被发现，因为演示器当时每 500ms 重发一次仓位 ——
> **演示的形态不真实，拿它做的验证就是假的**。演示器现在只在"成交"时发仓位，与真实柜台一致。

`walletKnown = false` 时页面会标出"未收到全量钱包快照，未列出 ≠ 0"：那份全量只来自启动对齐的
一次 REST 钱包查询，没到之前，"某币不在表里"不能读成余额为 0（依据见 `hft.domain.Wallet`）。

### 3. 只读，且默认只绑回环

没有任何写接口。看板是观察者，不是操作台 —— 一个能下单/停机的 HTTP 面意味着交易系统多了
一条不经过总线、不经过 `ActorSystem` 生命周期的旁路控制通道。真要做运维接口，那是另一个组件的事，
且必须走命令总线。

**没有鉴权**，而它把仓位、挂单、净值全摊开在页面上，所以默认 `host = 127.0.0.1`，
并且**校验 `Host` 头只接受 `127.0.0.1` / `localhost`**。

后一条是挡 DNS rebinding：只绑回环意味着"只有本机能访问"是唯一的防线，而浏览器会替攻击者破掉它 ——
操作者打开的任意网页，只要把自己的域名解析到 127.0.0.1，就能以**同源**读走 `/api/board` 的全部内容。
Host 白名单堵住这条路，且不影响 SSH 端口转发（转发之后 Host 仍是 localhost）。

要从别的机器看，走 SSH 端口转发：

```
ssh -N -L 8123:127.0.0.1:8123 user@trading-host
```

不要图省事绑 `0.0.0.0`。

## 失败语义

**端口绑不上 = 装配期失败，引擎起不来。** 这是有意的：端口冲突通常说明上一个进程还活着，
而两个进程同时管同一批仓位，比没有看板危险得多。

这里有一处必须自己确认的事：Helidon 的 `start()` 在绑定失败时**不抛异常** —— 它只在自己的
logger 上打一条 ERROR、把服务器停掉，然后正常返回，`port` 变成 `-1`。照单全收的话，日志里会印出
`看板已启动: http://127.0.0.1:-1` 而引擎照常往下跑。所以 `onStart` 在 `start()` 之后显式校验
`isRunning && port > 0`，不成立就抛。

运行期 HTTP 请求里的异常由 Helidon 自己处理，不会回到 actor 线程 —— actor 线程上只跑
`BoardSnapshot.apply` 那个纯折叠。

## 扇出与背压

看板用 `Interest.All` 全量订阅 10 个 topic，是总线上扇出最大的订阅者。**没有为它做采样或限流**，
理由是框架已经有答案：

- 邮箱**无界**，发布方不会因为看板慢而阻塞（`EventBus` 的既定判断：有界 + 尽力投递会在队列满时
  静默丢事件，而丢一条成交回报的后果是仓位长期不一致且无症状）；
- 看板是普通 `Actor`，因此自动纳入 `MailboxMonitor` 的滞后告警 —— 真跟不上时会打出
  `组件 dashboard@8123 邮箱滞后: queued=… oldestMs=…`（阈值 queued ≥ 10000 或最老事件 ≥ 5s）。

这正是框架"背压在消费者侧暴露、不靠丢事件掩盖"的既定姿态，看板照做即可，不需要自己那一套。
`DashboardActorSpec` 有一条 5 万条 BBO 的突发用例，断言邮箱能排空。

一点要清楚：看板是系统里的**普通组件**，`fold` 抛异常会触发全系统有序停机。所以
"它算错了不会下错单"成立，"**它炸了不影响交易**"**不成立** —— 折叠因此保持为全函数，
唯一会抛的是"收到未声明的 topic"，而那种情况已由上面那张表在编译期堵死。

实测（`StockSpreadLauncher` 接三家所真实行情）：

| 规模 | 事件率 | 心跳 |
|---|---|---|
| 15 个标的（5 个代码 × 3 所） | ~46 /秒 | — |
| **376 个标的（全量宇宙）** | **~978 /秒** | **1ms** |

全量宇宙下心跳 1ms 意味着折叠在实时跟上、邮箱没有积压，无滞后告警。真到了扛不住那天，
滞后告警会先说话 —— 到那时再谈采样，而不是现在凭空加一个旋钮。

一个已知的**页面**问题（不是总线问题）：376 个标的就是 376 行，且每秒序列化一次完整 JSON。
再大一个量级就该按交易所/关键字筛选或分页了。若同进程还跑全市场 `Trade` 源，
`Interest.All(Topics.Trade)` 会让行数再涨一截 —— 那时应把 `Trade` 从默认订阅里拿掉。

## 页面为什么是一个 HTML 字符串

不引任何 CDN：这东西跑在交易机上，而交易机可能没有外网、或者外网正好是出问题的那一环 ——
页面依赖第三方域名意味着"行情断了想看看板"的时候看板自己也打不开。

同理不做前端构建：换来的是"编译出来就能跑，没有第二套工具链"。页面复杂到需要构建工具的那天，
它也该是另一个仓库。

## 装配顺序：必须先于 `addStrategy`

全量 `Wallet` 与对齐时的初始仓位快照**只在启动对齐时发一次**（见 `TradingGateway.syncEvents`）。
看板若在 `addStrategy` 之后才 `install`，就永远收不到它们：`walletKnown` 一直是 false、
仓位一直显示 `—`，直到下一笔成交才有数。

失效是**可见的**（页面如实标出"未收到全量钱包快照"），不会骗人，但装错顺序就白等。
所以：先 `install(DashboardActor(...))`，再 `addStrategy(...)`。

## 分层与测试

| 文件 | 职责 | 测试 |
|---|---|---|
| `BoardSnapshot` | 纯折叠 `(快照, 事件) => 快照`，不读墙钟、不做 IO；**订阅列表由折叠表派生** | `BoardSnapshotSpec` |
| `BoardView` | 快照 -> 线格式，年龄按传入的 `now` 算 | `BoardViewSpec` |
| `DashboardApi` | tapir endpoint + Host 白名单，只依赖 `() => BoardView` | `DashboardActorSpec`（Host 头用裸 socket 测） |
| `DashboardPage` | 自包含 HTML | `DashboardActorSpec`（断言不含外部地址） |
| `DashboardActor` | 订阅、引用替换、HTTP 生命周期 | `DashboardActorSpec`（端到端 + 端口释放 + 绑定失败） |

领域类型用 opaque type 表达单位（`Coin`/`Price`），那是**进程内**的防线；出到 JSON 只能是数字，
由 `BoardView` 这一层显式解包 —— 解包点集中在一处，而不是散在各个 codec 的隐式推导里。
